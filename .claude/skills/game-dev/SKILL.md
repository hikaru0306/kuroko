# ゲーム制作

依頼: $ARGUMENTS

## エンジン選定(2026年時点)

| エンジン | 選ぶ場面 | 補足 |
| --- | --- | --- |
| **Godot 4.4+** | 2D全般、個人〜小規模、OSS志向 | 2D専用パイプライン(専用物理・タイルマップ・2Dライト・AnimationTree)が最強。エディタ約120MBで軽量、ライセンスリスクゼロ。GDScript/C# |
| **Unity 6** | モバイル、巨大エコシステムが必要 | モバイル市場シェア約48%、トップグロスの約70%。Runtime Fee廃止済み。C# |
| **Unreal 5** | AAA級グラフィック、大規模制作 | World Partition、Sequencer、Control Rig、標準マルチプレイヤー複製。収益$1Mまでロイヤリティなし。C++/Blueprint |
| **Webブラウザ(素のJS/Canvas/Phaser)** | 配布最優先の小品、ゲームジャム、プロトタイプ | ビルド不要で即共有。このリポジトリでの試作にも最適 |

迷ったら: コアメカニクスの縦切り(vertical slice)を最有力候補で1週間以内に作って判断する。

## 制作の進め方

1. **コアループを1文で定義**: プレイヤーが繰り返す行動と、それが生む報酬・成長(例: 「避けて撃つ→強化を選ぶ→より強い敵」)。これが面白くなければ他の何を足しても面白くならない。
2. **最小プレイアブルを最短で**: グレーボックス(仮アセット)でコアループだけ動かす。アート・音・メニューは後。この時点で /fable-verify 相当のプレイテストをする。
3. **ゲームフィールを盛る**: 面白さの大半は手触り。入力バッファ、コヨーテタイム(崖から数フレーム猶予)、ヒットストップ、画面シェイク、squash & stretch、パーティクル、SEの即時性。数値は感覚で調整し、必ず定数として1箇所に集める。
4. **拡張**: レベル/敵バリエーション → 進行(アンロック・難易度カーブ) → メタ(セーブ、スコア、設定)。
5. **バランス調整**: パラメータは外部データ(JSON/CSV/Resource)に出し、リロードなしで調整できるようにする。難易度は「初見が3回目で越えられる」を基準に。

## 実装の定石

- **状態管理**: プレイヤーや敵はステートマシン(idle/run/jump/attack/hurt)で書く。フラグの山にしない。
- **update分離**: 入力→ロジック→物理→描画の順序を固定。可変フレームレートでは deltaTime を必ず使い、物理は固定タイムステップに。
- **オブジェクトプール**: 弾・パーティクルなど大量生成物は生成/破棄でなくプールで回す。
- **シーン構成**: Godotはシーン=プレハブとして小さく合成、Unityはプレハブ+ScriptableObjectでデータ駆動、UnrealはBlueprintで組んでからホットパスのみC++化。
- **セーブ**: JSONで単純に。バージョンフィールドを最初から入れる。

## AI活用(2026年の標準)

音楽・効果音・スプライト・ボイスのAI生成で個人でも小チーム相当の物量が出せる。ただしコアループとゲームフィールは手で作り、手で調整する — そこが面白さの本体。

## 落とし穴

- コアループ検証前のアート制作・大規模設計(ECS導入など)は時期尚早。
- スコープ過大が未完成の最大原因。「削っても成立する要素」から着手しない。
- プレイテストなしの難易度調整は必ず難しすぎになる(作者は上手すぎる)。
